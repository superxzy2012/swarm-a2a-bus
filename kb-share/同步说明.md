## 2. 同步路径结论

- **同步枢纽 = GitHub**。理由：NAS 无公网 IP、无 Tailscale，云端可达 NAS 的现实通道只有经中继转发 + SFTP 只写投递口（账号 muse-delivery，无 shell，只能投递 `incoming/muse`，不能读写 vault 主本）；而 GitHub 总线 `superxzy2012/swarm-a2a-bus` 是云端与 NAS 侧（小卡 xiaoka-relay 持续同步）双向已通的枢纽。NAS Gitea 只是 GitHub 的单向镜像备份，不作同步枢纽。
- **两种仓形态（需 BOSS 拍板）**：
  - **首选：新建 GitHub 私有专用 KB 仓**。利：与任务文件分仓、权限粒度细、可独立控制读写；弊：需 BOSS 拍板新开仓，NAS 侧需新增一处拉取配置。
  - **过渡：总线仓 `kb-share/` 子目录**。利：通道现成、立即落地、xiaoka-relay 已在同步；弊：与任务文件混仓、权限粒度粗、仓体积随知识增长膨胀。**过渡路径先行落地**，专用仓拍板后整体迁移，目录结构不变。
- **流向**：
  1. 云端（Muse 及各 agent）只向总线 muse 分支的 `kb-share/00-投稿区/` 投稿，不直改正式目录、不直改 NAS 主本。
  2. NAS 侧由小卡在 NAS 上拉取 GitHub（经 xiaoka-relay 同步到本地后）内容，审核通过后合并进 vault 主本的对应目录；合并后回推「目录清单 / 变更回执」到总线，供云端核对版本。
  3. 各 agent 只读拉取同一版本读知识，不各自存一份改一份。
- **技能库同理**：NAS 361 与 Mac 336 先双侧导出清单对账（名称+路径），再定中央仓标准（SKILL.md 骨架，见方案稿 B3），中央仓同样以 GitHub 为枢纽、NAS 侧经小卡拉取落地；对账完成前不定迁移清单。

## 3. 投稿流程

1. 投稿人把新内容写入云端副本 `00-投稿区/`（文件名带日期 YYYYMMDD 与主题，注明来源任务/回执编号）。
2. 随工单或提交同步到总线 muse 分支 `kb-share/00-投稿区/`。
3. 审核：Muse 初审；涉及口径与平台规则的由 BOSS 或 QUEEN 终审（终审分工待 BOSS 拍板，见方案稿待拍板事项 2）。
4. 小卡在 NAS 侧拉取并合并进 vault 主本对应正式目录，回执带目录清单证据与 commit/变更说明。
5. 未通过审核的投稿留在投稿区并注明原因，不删除；作废内容移入 `99-归档/` 并注明依据。
