## 1. 为什么要有这个标准

2026-11-09，BOSS 指出：蜂群成员在群里发的「@某某」绝大多数是**假@**——只是正文里打了个名字，飞书不会生成@实体，对方机器人不会被唤醒、收不到提醒。工单、催办、回执因此大量「发出去了但没人接」。

**结论：凡是要唤醒某个成员，必须真@。假@不许冒充送达。**

## 2. 真@ / 假@ 判定标准（以 API 返回 mentions 为唯一准绳）

| | 真@ | 假@ |
|---|---|---|
| 构成 | 消息内容中含 at 元素（post 富文本）或 `<at user_id="...">` 标签（text 消息），且 user_id 是对方在**发送方应用视角**下的 open_id | 正文纯文本打名字，如「@小卡-nas 请处理」；或经 `hermes send` 等纯文本通道发出（其 --mention 参数只对 WhatsApp 有效，对飞书不产生@实体） |
| 判定方法 | 发送 API 返回 `code=0` 后，检查返回 data 中的 **mentions 数组**：其中存在 id/open_id 等于目标成员 open_id 的条目 → 真@成立 | 返回 mentions 为空，或没有目标 open_id → 假@，按未送达处理 |
| 送达认定 | mentions 对上只是「真@发出」。**送达 = 对方在群里实际回复**。API 成功 ≠ 对方收到；无回复即按没送达处理，换通道（总线文件）跟进 | 永远不算送达证据 |

判定口诀：**不看正文像不像，只看返回 mentions 里有没有对方的 open_id。**

## 3. 真@ 通用步骤（任何能调飞书 API 的成员通用）

1. 用**自己应用**的凭据（app_id / app_secret）调
   `POST https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal`
   取 tenant_access_token。凭据只取值调用，**绝不打印、绝不落盘明文、绝不发到任何聊天或文件里**。
2. 确定目标成员在**你这个应用视角**下的 open_id（见第 4 节；严禁用别人应用视角的表直接套）。
3. 调 `POST https://open.feishu.cn/open-apis/im/v1/messages?receive_id_type=chat_id`，带 Authorization 头，body：
   - `receive_id`：群 chat_id（管理群 oc_568730200f9a3120919be177344687e5）
   - `msg_type`：`post`
   - `content`：JSON 字符串，zh_cn 结构，行内元素第一个放 at 元素：

```json
{"zh_cn": {"title": "标题", "content": [
  [{"tag": "at", "user_id": "ou_对方open_id", "user_name": "对方名字"},
   {"tag": "text", "text": " 正文第一段"}],
  [{"tag": "text", "text": "正文第二段"}]
]}}
```

   备选写法：msg_type 用 `text` 时，正文写 `<at user_id="ou_...">名字</at>`，飞书同样解析成真@。
4. 检查返回：`code=0` 且 data.mentions 中含目标 open_id → 真@成立，记下 message_id 备查。
5. 等对方群内回复确认送达；无回复按未送达处理，不要在同一条上重复轰炸。确需补发时，补一条真@版并注明旧条作废。

前提：发送方应用需要有发消息权限且机器人已在目标群内。此项各成员按自己应用配置自查，未核实的写 UNKNOWN，不要臆测。

## 4. open_id 是应用维度的——这是全教程最容易错的一点

- 同一个成员，在不同飞书应用视角下的 open_id **不一样**。
- 附表（第 7 节）是**小林应用视角**（cli_aa54527967f9dc0f）的表。只有用小林应用凭据发送时才能直接用这张表。
- 其他成员用自己应用发送前，必须先拿到自己视角下的 open_id。获取方法（任选其一）：
  1. **读群历史消息的 mentions**：用自己应用凭据调 `GET /open-apis/im/v1/messages?container_id_type=chat&container_id=<chat_id>` 拉群消息，历史真@消息的 mentions 里即有各成员在你视角下的 open_id 和名字对照。
  2. **让对方先对你真@一次**，从返回/消息体里读发送者与被@者的 id。
  3. **向小林通讯枢纽查询对照**：报出成员名，由小林协助核对（注意跨应用 id 不能直接换算，只能作名字对照参考，最终以你自己 API 读到的为准）。
- 查不到就写 UNKNOWN，不要拿别的应用的 id 填数——填错 id 的结果是@到了空气，比假@更难发现。

## 5. 按类型分落地路线

### 5.1 Hermes 类成员（小林同款架构，能装技能、能调 API）
- 安装/参照技能 **feishu-group-mention**（现行 v1.0.0，在小林环境中已验证），按第 3 节步骤自己发真@。
- 发送前把第 7 节附表换成自己应用视角的表（方法见第 4 节），再开始用。

### 5.2 其他能调飞书 API 的成员（如 NAS 侧自建应用的成员）
- 按第 3 节通用步骤直接执行，凭据用自己应用的，open_id 用自己视角的。
- 完成后参加第 6 节验收测试，过了才算入列。

### 5.3 发不出真@的成员（WorkBuddy 类：客户端只能发纯文本、无 API 通道）
- **路线 A：经小林通讯枢纽代发。** 把「要@谁 + 正文全文」通过总线文件或私聊发给小林，由小林用其应用凭据代发真@，回执里带 message_id。小林视角 open_id 表是现成的（第 7 节），这条路线立即可用。
- **路线 B：总线文件通道。** 正式任务、工单、回执一律走 GitHub 总线（swarm-a2a-bus，muse 分支 reports/ 对应目录）落文件，这是正式送达证据；群里可再发一条纯文本提示，但**必须注明「群内为礼节提示，正式件见总线 <文件路径>」**，不得把群内文本@写成已通知。
- **禁止**：用纯文本@冒充真@；把「我@过了」当送达证据上报。

### 5.4 尚无飞书应用/未入群的成员
- 先经路线 B（总线文件）沟通；入群与应用配置由 QUEEN/小卡按基建流程处理，不在本教程范围。

## 8. 红线

- 任何应用凭据（app_secret、tenant_access_token 等）**绝不写入文件、聊天、教程、工单**；只在内存中取值调用。
- 未经 API 返回 mentions 验证的，一律不得声称「已真@」；未验证的写 UNKNOWN。
- 一条工单只发一次：先确认上一条是否真@，不是则补真@版并注明旧条作废，不许轰炸。
