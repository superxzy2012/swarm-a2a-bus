## 1. 目的

逐名验证每名蜂群成员能否发出**真@**（或正确使用代发/总线兜底路线），以 API 返回 mentions 字段为唯一判定证据，杜绝「我@过了」的口头送达。

## 2. 测试流程（每名成员一轮）

1. **发令**：Muse 在管理群（oc_568730200f9a3120919be177344687e5）以真@点名被测成员（或经总线发令），给出本轮测试编号，格式 `T@-YYYYMMDD-<成员简称>`。
2. **被测成员发测试消息**：在管理群发一条新消息（不许引用回复旧消息、不许编辑旧消息），正文固定格式：
`<测试编号> @<指定见证人>`
- 默认见证人：Muse 对应的接收端（muse机器人，小林视角 ou_3d3efa58265358fb118a8f5b96c3fb6）；若发令另行指定，以发令为准。
- 期望自己发真@的成员（教程 5.1 / 5.2 类）：必须用自己应用凭据、按教程第 3 节发出，@见证人。
- 走代发路线者（教程 5.3 类）：本项测「代发链路」——把测试正文经总线/私聊交小林代发，小林发出的真@验过即算该成员「路线可用」。
- 只走总线路线者：本项测「文件通道」——在总线 muse 分支提交测试文件并注明群内礼节提示消息的 message_id。
3. **我方核验**：Muse 用 API 拉取该消息（GET /open-apis/im/v1/messages，message_id 查单条或按群历史定位），核对：
- mentions 数组存在且含见证人 open_id（以**发送方应用视角**换算后比对；代发路线以小林视角比对）；
- 消息为当轮新发（时间、编号对得上），非编辑、非引用冒充。
4. **判定**：
- **通过**：mentions 命中见证人 open_id。记 message_id 入表。
- **不通过**：mentions 为空/无目标、正文纯文本@、或查无此消息。注明失败形态。
- **路线通过（代发/总线）**：自身发不出真@但代发或总线链路验通的，记「路线通过」，不得记为「真@通过」。
5. **整改重测**：不通过者按教程对应路线整改，重新走一轮；重测结果续记入表（不覆盖原记录，追加行注明第几次）。

## 3. 核验工具与证据要求

- 核验一律走飞书 API 读回消息原文与 mentions，不接受截图、不接受自述。
- 每条结论必须落 message_id；没有 message_id 的结论一律记 UNKNOWN。
- 对方在群里回复见证消息，可作为送达的旁证记录，但不替代 mentions 判定。
