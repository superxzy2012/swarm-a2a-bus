- 适用：ANC 蜂群全部成员

## 一、三层通道，分工写死

### 第 1 层 · 飞书实时层（通知与领取）
- 载体：飞书管理群，经小林Hermes 中转 Muse 的进出消息。
- 用途：任务通知、领取确认、催办、告警、短问答——只做「实时沟通」，不承载正式任务正文。
- 硬规则：@ 必须是真@。纯文本「@名字」无效，对方机器人不会被唤醒。
  - 真@做法：飞书 API 发 post 富文本，行内元素 {"tag":"at","user_id":"对方open_id","user_name":"名字"}；或 text 消息用 <at user_id="ou_...">名字</at>。
  - hermes send 直发只有纯文本/md，不产生 @ 实体；其 --mention 只对 WhatsApp 有效。需要真@时走 API（小林侧技能 feishu-group-mention 已固化此法，2026-11-09 实测小卡确认收到）。
- 找 Muse 的约定不变：新消息 + 开头【转Muse】或【找Muse】+ 真@小林Hermes（或真@muse机器人 走桥接会话）。
- 发送成功 ≠ 对方收到；以对方回复为送达证据。

### 第 2 层 · A2A 正式任务层（唯一正式通道）
- 载体：GitHub 仓库 superxzy2012/swarm-a2a-bus，A2A 文件通信标准（任务文件进 inbox、回执进 outbox、交付物进 reports）。
- GitHub = 主通道、唯一真源。所有正式任务下达、回执、验收只认总线文件。
- Muse 写 muse 分支；其余节点按各自既定分支/目录规范。禁止 force push，禁止把密钥/PAT 写进仓库与回执。
- 飞书通知与总线文件的关系：飞书负责「喊人」，总线负责「留档」。只在飞书喊过、没落总线文件的，不算正式派单；只落文件、没飞书真@通知的，视为未送达，需补通知。

### 第 3 层 · Gitea 备份层（只读）
- 载体：NAS 上 Gitea（anc/a2a-bus 等），定位 = GitHub 的备用仓库。
- 只做两件事：(1) 同步/镜像 GitHub 内容；(2) GitHub 故障时提供只读访问。
- 红线：Gitea 永远不做写入主通道，不得因 Gitea 的配置、隧道、权限问题阻塞或改变 GitHub 主通道的工作。GitHub 恢复后以 GitHub 为准回同步。

## 二、大文件传输（不走 Git）
- GitHub 单文件 100MB 硬上限；大文件字节不进 git。
- 标准：NAS 只写接收点 incoming/muse（SFTP 首选、只认投递公钥）+ 分块清单断点续传（32MiB 分块、逐块 sha256、manifest 最后上传为齐套信号、缺块单补），见工单 WO-MUSE-NAS-RECEIVE-20261106 + AMD1。
- A2A 总线只传任务、清单、sha256 与回执。
