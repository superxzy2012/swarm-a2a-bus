## 1. 现状

### 1.1 已知

- 蜂群的正式事实目前散落在三处：A2A 总线仓的任务文件与回执文件（GitHub muse 分支）、飞书管理群的通知与纪要、管理群之外的各类文档与知识库文件。没有任何一个统一入口能跨这三处检索。
- 总线侧已有可追溯的凭证习惯：任务有编号、回执落文件、关键动作有 commit / message_id 可查。这是做共享记忆最好的原始素材，不需要推倒重来。
- 各 agent 各自有本地记忆（如 Hermes 的 memories、Muse 的个人记忆系统），但格式互不相通、彼此不可见，本质是「每人记自己的」，不是蜂群共享记忆。
- 通道分工已经定版（见文首关联口径）：实时通知归飞书，正式任务与回执归 A2A 文件。因此记忆系统的原始层必须建在文件侧，不能建在聊天记录侧。
- NAS 是蜂群的本地枢纽（Gitea、接收点均在 NAS），具备集中部署一个检索服务的物理落点；云端节点（Muse 所在 VM）内存紧张、无固定公网 IP，不适合承载常驻检索服务。

### 1.2 未知（施工前必须先核查，不得假设）

- NAS 的硬件余量未知：CPU / 内存 / 可用磁盘、是否可跑 Docker 常驻服务、是否有 GPU，直接决定向量库与 embedding 模型的选型档位。**待小卡核查回执。**
- 总线历史总量未知：muse 分支至今的任务 / 回执文件数与总字数未盘点，索引规模是千级还是万级文档未定。**待 Muse 在总线恢复后盘点（总线部署密钥正在由小卡恢复中）。**
- 各 agent 本地记忆的可导出性未知：除 Hermes 外，其余节点（WorkBuddy / Codex 等）的记忆格式与导出方式未摸排。P0 阶段不依赖这一项，P2 前需逐个确认。
- NAS 上知识库文档的存量与质量未知（与《03-知识库与技能库共享方案》联动核查），入库前需先有目录清单。
- 飞书侧纪要的留存形式未知：哪些会议有成文纪要、存在哪里，未盘点前不把飞书纪要列为 P0 数据源。

## 2. 目标

1. **蜂群共享记忆**：任务、回执、决策、教训四类内容，全蜂群可按统一入口检索，不再靠某个 agent「记得」或靠 BOSS 转述。
2. **答案必带出处**：任何检索结果必须能回溯到原始文件路径 / commit / 消息凭证；查不到就明确返回「无记录」，不许凭模型记忆补答。
3. **写入有门槛**：记忆不是谁想写就能写。没有回执凭证的内容不入库，杜绝无源记忆和传闻记忆。
4. **本地优先、成本可控**：服务部署在 NAS，数据不出内网；云端只做脚本、规范和验收，不新增付费服务（新增付费项一律先报 BOSS 拍板）。

非目标（本规划不做）：不做 agent 之间的实时记忆同步（那是通讯问题，不是检索问题）；不替代 A2A 总线，总线仍是事实源，记忆系统只是它的索引；不收录 BOSS 的个人记忆（Muse 个人记忆系统与蜂群共享记忆严格分开）。

## 3. 分层设计

### 3.1 原始层（事实源，只存原文，不存结论）

- A2A 总线仓文件：任务单、回执、工单、验收记录（GitHub muse 分支为源，Gitea 只读镜像为备份）。
- 知识库文件：Obsidian vault 中的决策 / SOP / 教训 / 模板（见 03 号方案）。
- 纪要文件：经确认成文的飞书会议纪要、日报周报的落盘副本。
- 原则：原始层只增不改；原文修正走新版本文件 + 旧版标记作废，不直接覆盖，以便索引可重建、可审计。

### 3.2 索引层（向量 + 全文混合检索）

- 对原始层文档做切分（chunk），每块同时建两类索引：
  - **向量索引**：语义检索，解决「换个说法也能找到」。
  - **全文索引（BM25）**：关键词检索，解决任务编号、文件名、专有名词这类必须精确命中的查询。
- 两路结果合并后重排（rerank）输出。只上向量一路，查任务编号必翻车；只上全文一路，查「上次那个断点续传的结论」必翻车，两路都要。
- 每块必带元数据：`source_type`（任务/回执/决策/教训/纪要）、`source_path`、`commit` 或凭证号、`author`（哪个 agent）、`date`、`weight`（权重等级，见第 6 节）、`status`（有效/已作废/待复核）、`review_by`（建议复核日期）。

### 3.3 服务层（统一查询接口）

- 在 NAS 上提供一个统一查询接口（HTTP API，仅内网 / 尾网可达），入参是自然语言问题 + 可选过滤（类型、时间、来源），出参是「原文片段 + 出处 + 权重 + 日期」列表，不直接输出模型拼凑的长答案。
- 各 agent 通过同一种方式调用：能调 HTTP 的直接调；只能走文件的 agent，由总线代办——在总线发查询单、由 NAS 侧服务回结果文件。两种方式返回结构一致。
- 是否在接口之上再加一层「LLM 读片段后作答」由调用方 agent 自己决定，服务层不内置生成，避免出处在生成环节丢失。

## 4. 技术选型建议（NAS 本地部署优先）

### 4.1 首选组合

- **向量库：Qdrant**（单机 Docker 部署在 NAS）
  - 理由：单节点即可运行、运维面小、自带全文/稀疏向量能力便于做混合检索、数据目录就是本地文件夹、备份与迁移简单；规模（蜂群文档量级）远在其能力下限内，不需要集群。
  - 备选一：**pgvector**（PostgreSQL 扩展）。若 NAS 上已有 PostgreSQL 在跑，选它可以少养一个服务，且元数据过滤用 SQL 很顺手。缺点是混合检索与重排要自己拼。
  - 备选二：**sqlite-vec**（超轻量）。若小卡核查后 NAS 资源非常紧，可作 P0 降级方案：零常驻服务、一个文件就是一个库。缺点是并发与规模上限低，只适合验证期。
  - 不推荐：Milvus 等重型向量库——组件多、吃资源，对蜂群当前量级是杀鸡用牛刀，运维成本反而最高。
- **Embedding 模型：bge-m3**（本地运行）
  - 理由：中英双语友好（蜂群文档中英混排）、同时产出稠密 + 稀疏向量、一套模型支撑混合检索、开源可本地跑、数据不出 NAS。
  - 备选：bge-large-zh-v1.5（纯中文场景更专，但英文与稀疏能力弱于 bge-m3）；若 NAS 无 GPU 且 CPU 推理太慢，先用小档模型跑通 P0，再按验收数据决定是否升级，**不先买云端 embedding API**（要花钱且文档出内网，需 BOSS 单独拍板）。
- **重排（可选，P1 再上）**：bge-reranker 系列本地小模型，只对合并后的前若干条重排，成本低、对引用准确率提升明显。

### 4.2 部署边界

- 服务只监听内网 / 尾网地址，不开公网端口；云端 Muse 不直连向量库，走总线文件或经已批准的内网通道调用查询接口（具体通道方式待小卡给出 NAS 网络现状后定，不预设）。
- 索引可随时由原始层全量重建——索引丢了不算事故，原文丢了才是。备份优先级：原始层 > 元数据表 > 向量索引。

## 5. 数据来源与入库流水线

### 5.1 数据来源（按优先级）

| 来源 | 内容 | 入库阶段 |
|---|---|---|
| A2A 总线回执与任务文件 | 任务单、回执、工单、验收结论 | P0 起 |
| BOSS 决策与红线文档 | 拍板记录、口径变更、红线文件 | P0 起（最高权重，人工确认后入库） |
| 知识库文档 | Obsidian 的 SOP / 教训 / 模板 | P1（待 03 号方案核查完成） |
| 飞书纪要（成文落盘的） | 会议纪要、日报周报 | P1（先盘点留存形式） |
| 各 agent 本地记忆导出 | 经属主确认可共享的部分 | P2（逐个确认格式后再议） |

### 5.2 入库流水线（每一步可单独重跑）

1. **采集**：从总线仓 / 知识库目录拉取新增或变更文件（按 commit / 文件时间戳识别增量）。
2. **凭证校验**：文件必须能标明来源与凭证（commit、任务编号、回执编号、纪要对应的消息凭证，任选其一可查证）。**校验不过，不入库**，只记入待核清单。
3. **清洗与切分**：去模板噪音，按标题与段落切分，单块长度设上限；表格类内容整表成块，不拦腰切断。
4. **打元数据**：按 3.2 的字段表打标；权重按第 6 节规则定级，定不了级的默认最低权重并标「待定级」。
5. **向量化与入索引**：bge-m3 本地推理，写入 Qdrant，并同步更新全文索引。
6. **出处登记**：每块生成一条出处记录（块 id → 原始路径 + commit），随索引一同保存，查询返回时强制携带。
7. **入库回执**：每批入库产出一份回执文件落回总线（本批多少文件、多少块、多少条被凭证校验拦下），蜂群可查，Muse 据此验收。

## 6. 权限与属主

- **权重分级**（检索重排与答案采信都按此序）：
  1. 最高：BOSS 的决策、口径与红线文档（与之冲突的低权重记忆自动降权并标冲突）；
  2. 次高：经 QUEEN / 贾维斯验收过的回执与审计结论；
  3. 一般：各 agent 的任务回执、工单、日报；
  4. 最低：未验收的过程记录、纪要草稿、待定级内容。
- **属主规则**：每条记忆有属主（写入的 agent 或确认入库的人）。属主负责其内容的复核与作废申请；他人不得改属主名下记忆，只能追加「异议标注」走回执说明。
- **写入门槛**：写入必须附回执凭证（总线 commit / 回执编号 / 飞书消息凭证三选一）。**禁止无源写入**，包括禁止把某 agent 的口头结论、模型推测直接写成「事实记忆」。
- **读取范围**：默认全蜂群可读已入库内容；BOSS 个人事项、密钥与账号类信息**永不入库**（这类内容不属于蜂群记忆，入库流程要在采集环节就过滤掉，过滤规则由 Muse 出清单、小卡在 NAS 侧执行）。
- **作废机制**：记忆不删除、只标记作废并注明依据（哪份新决策 / 回执取代了它），检索默认不返回已作废条目，但可按需查历史。

## 7. 分阶段落地

### P0 — 只读检索总线历史（验证期）

- 步骤：
  1. 小卡核查 NAS 资源（CPU / 内存 / 磁盘 / Docker 可用性），出回执。（小卡）
  2. Muse 盘点总线历史文件清单与总量，出入库范围清单。（Muse，总线恢复后）
  3. 小卡在 NAS 部署 Qdrant + bge-m3（Docker，内网监听），出部署回执含访问方式。（小卡）
  4. Muse 编写入库脚本 v0（只处理总线任务 / 回执两类）与查询客户端，在云端先用小样本自测。（Muse）
  5. 首批入库 + 入库回执落总线；用第 8 节的测试题集验收。（Muse 验收，小卡配合）
- 产出：一个能查总线历史的只读检索服务，哪怕慢，先证明「找得到、带出处」。

### P1 — 自动入库

- 步骤：
  1. 入库流水线改增量自动跑（总线有新回执 commit 后自动触发或定时增量），含凭证校验与过滤规则。（小卡在 NAS 挂调度，Muse 出脚本与规则）
  2. 数据源扩到知识库文档与成文纪要（依赖 03 号方案的核查结论）。（Muse + 小卡）
  3. 上重排模型，调切分与权重参数，用同一题集复测对比 P0。（Muse）
  4. 作废 / 冲突标记流程上线：新决策入库时自动提示与之冲突的旧记忆。（Muse 出规则，小卡执行部署）
- 产出：记忆库从「人工喂」变「总线一有回执就自动进库」。

### P2 — 跨 agent 共享查询

- 步骤：
  1. 统一查询接口定稿（请求 / 返回结构、过滤字段、错误码），写成 A2A 侧约定文件落总线。（Muse）
  2. 逐个 agent 接入：能调 HTTP 的直连；只能走文件的用总线查询单代办。每个接入出一条接入回执。（各 agent 属主，小米协助代码侧适配，Muse 验收）
  3. 各 agent 本地记忆的可共享部分，经属主确认后开始导出入库（第 5.1 表最后一行）。（各 agent 属主拍板内容，BOSS 拍板总原则）
  4. 做一次全蜂群演练：同一个问题分别问三个 agent，比对是否都引用同一出处。（Muse 组织，结果报 BOSS）
- 产出：共享记忆从「Muse 能查」变成「全蜂群在用」。

## 8. 验收标准

- **可查**：预置测试题集不少于 20 题（覆盖任务编号精确查、教训语义查、决策原文查三类），P0 验收要求前 5 条结果内命中正确原文的比例 ≥ 90%。
- **带出处**：抽查 20 条返回结果，出处（路径 + commit / 凭证）完整率 100%；有一条无出处即不算通过。
- **不编造**：预置 5 题「蜂群从未发生过的事」，系统必须明确返回无记录，出现编造答案即不算通过。
- **时效标记**：抽查含已作废内容的查询，默认结果不得把作废条目排在有效条目之前；超过复核日期未复核的条目必须带「陈旧待复核」标记返回。
- **回执齐全**：每个阶段的部署、入库、接入都必须有回执落总线，没有回执的阶段不算完成。
- **性能底线**：内网单次查询返回（不含 LLM 生成）在数秒量级内完成即可，不追高并发指标。

## 9. 风险与对策

- **幻觉引用**：最大风险。服务层只返回原文片段 + 出处、把生成留给调用方，就是为此。对策：出处登记与片段绑定生成，片段改一个字出处即失效；验收含「不编造」硬项。
- **陈旧记忆误导**：旧口径被新决策推翻后仍被查到。对策：作废标记 + 复核日期 + 权重分级三件套；BOSS 新决策入库时强制走冲突检查。
- **无源内容污染**：agent 把推测当事实写入。对策：凭证校验前置，无凭证只进待核清单，永不进正式索引。
- **单点在 NAS**：NAS 故障则检索不可用。对策：原始层在 GitHub 有主本、Gitea 有镜像，索引可全量重建；检索中断不影响总线本身运转，降级为人工翻文件。
- **敏感信息误入库**：对策：采集环节过滤清单（密钥、账号、BOSS 个人事项），过滤命中只记数不记内容；若发现已误入，按作废 + 索引清除处理并出回执说明。
- **模型更换导致索引漂移**：embedding 模型一换，全量向量需重算。对策：选型在 P0 定死并记录版本；换模型必须全量重建并复跑题集，不许新旧向量混存。
