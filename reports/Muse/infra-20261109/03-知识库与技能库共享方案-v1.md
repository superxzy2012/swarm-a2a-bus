## 总览

本方案含两部分，相互独立、可分别拍板分别施工：

- **A 部分 — 知识库共享**：第一知识库 = NAS 上的 Obsidian，先核查、再共享、跑通验收；之后才启动第二知识库 ima，作为补充，不替代 Obsidian。
- **B 部分 — 技能库共享**：先核查 Mac 上的 skill box 与 NAS 侧的部署现状，再定统一的技能包标准与中央仓，让全蜂群按同一标准发布与拉取技能。

共同原则：现状不清的先核查再设计细节；所有共享都走「中央仓发布 + 各端只读拉取 + 按规投稿」的模式，不搞点对点互相同步；每个阶段以回执验收，没有回执不算完成。

- 现行通道条件具备做 git 同步：GitHub 是主通道且各云端节点可达，NAS 侧有 Gitea 只读镜像可作备份，两端都有落点。

### A1.2 未知（待小卡核查，出回执后才算数）

- Obsidian 到底是否仍在 NAS 上部署：是装了 Obsidian 本体 / 同步服务（如某种 vault 同步方案），还是仅有过一个 vault 文件夹，**UNKNOWN**。
- 若 vault 存在：其路径、现有目录与文件量、最后更新时间，**UNKNOWN**。
- 现有同步方式（若有）：是 git、是 NAS 文件共享、还是某同步盘在同步，**UNKNOWN**。

- 以上四项由**小卡核查并出回执**（含截图或目录清单凭证），核查结论出来前，本节以下设计中的 vault 路径与同步细节均为草案，不得当作已确认事实施工。

## A2. 目标

1. 蜂群有一座**唯一的第一知识库**：决策、SOP、产品、平台规则、教训、模板六类长期知识，存放在 Obsidian vault，全蜂群可读、可按规投稿。
2. Obsidian 跑通并验收后，再启动**第二知识库 ima**，定位为阅读侧 / 对外侧补充，与 Obsidian 分工不重叠（见 A5）。
3. 知识库与记忆系统（02 号规划）衔接：vault 是记忆系统原始层的数据源之一，目录与命名按可被索引的要求设计。

## A3. 共享模型

- **vault 主本放 NAS**：NAS 上的 vault 目录为唯一主本，Obsidian 在 NAS 侧或 BOSS 的设备上打开编辑。
- **git 同步**：vault 纳入 git 管理，同步到一个 GitHub 私有仓（新建知识库专用仓，优先），或在 BOSS 不同意新开仓时，暂放总线仓的独立子目录（次选，缺点是与任务文件混仓、权限粒度粗）。Gitea 侧保持只读镜像，与主通道的既定分工一致。
- **各 agent 的权限**：
  - **只读拉取**：所有 agent 默认只有拉取（clone / pull）权限，按同一版本读知识，不各自存一份改一份。
  - **按目录投稿**：agent 不得直接改主本目录；新内容写入「投稿区」子目录（或投到总线由 Muse 汇总转投），经审核合并进正式目录。审核人选与节奏待 BOSS 拍板（默认建议：Muse 初审、涉及口径与规则的由 BOSS 或 QUEEN 终审）。
  - **禁止事项**：任何 agent 不得把未验收的结论写进「决策」「平台规则」目录；密钥、账号、BOSS 个人事项不得进入 vault。
- **版本与回溯**：靠 git 提交历史回溯，谁在何时改了什么必须可查；合并投稿时提交信息注明来源任务 / 回执编号。

## A4. 目录结构草案

```
vault/
  00-投稿区/          （agent 投稿先落这里，审核后合并）
  01-决策/            （BOSS 拍板与口径变更，最高权重，只收成文决策）
  02-SOP/             （标准作业流程，按业务线分子目录）
  03-产品/            （选品、SKU、供应链相关沉淀）
  04-平台规则/        （各平台规则与合规要点，注明核查日期与来源）
  05-教训/            （失败复盘、踩坑记录，注明对应任务/回执编号）
  06-模板/            （任务单、回执、报告、表格等空白模板，只放空白版）
  99-归档/            （已作废内容移此，不删除，注明作废依据）
```

命名约定：文件名带日期（YYYYMMDD）与主题；平台规则类必须在文内标注「核查日期 + 来源链接 / 凭证」，过期未复核的在文件头标「待复核」。

## A5. 第二知识库 ima 的定位（验收后才启动）

- **启动条件**：Obsidian 第一知识库完成 A6 的全部验收项之后，才讨论 ima 的开通与接入；**ima 目前未开通，本方案不把它写成既成事实**，其具体功能形态以届时实际产品能力为准，先定分工、后定细节。
- **分工**：
  - Obsidian（第一知识库）= **蜂群内部的事实与作业知识**：可编辑、可版本管理、数据在自己 NAS 上，是唯一的内部主本。
  - ima（第二知识库）= **阅读侧 / 对外侧补充**：适合放整理好的、供阅读检索的内容（如平台规则汇编、产品资料、对外可分享的沉淀），以及利用其阅读与问答体验做消费端入口；不作内部主本，不存未验收内容与敏感内容。
- **同步方向**：只允许 Obsidian → ima 单向发布（从主本挑已定稿内容发布过去），禁止 ima 侧内容回流覆盖 Obsidian 主本。

# B 部分：技能库共享（skill box 现状核查 + 统一技能仓）

- 已有可参考的样本：Muse 与 Hermes 两侧都在用 SKILL.md 作为技能说明文件，「一个技能一个目录、目录里有说明文件」是两边共同的骨架，统一标准有现实基础，不是另起炉灶。

### B1.2 未知（待核查，出回执后才算数）

- skill box 或任何技能库是否曾部署 / 同步到 NAS，**UNKNOWN**。**待小卡核查 NAS 侧**（查有无同名目录 / 仓 / 服务）。
- 其余节点各自现存的技能 / 模板资产清单，**UNKNOWN**，B-1 阶段一并摸排，不逐个预设。
- 两份核查回执出来前，B3 的迁移步骤只定标准与流程，不定具体迁移清单。

## B2. 目标

1. 蜂群技能资产有一座**中央仓**：所有可共享技能按统一标准存放、带版本与属主，全蜂群按需拉取，不再各存一份野版本。
2. 技能格式以 SKILL.md 为通用骨架，并给出与 Hermes skills、Muse custom-skills 之间的**格式映射**，让同一技能在不同体系里能落地，而不是强迫所有节点改造成同一体系。
3. skill box 的存量：能救的按标准迁移进中央仓，不能救的列清单报 BOSS 后归档，不默默丢弃、也不默默沿用。

## B3. 统一方案

### B3.1 技能包标准结构

每个技能一个独立目录，中央仓内结构如下：

```
skills/<技能名>/
  SKILL.md          （必需：技能说明正文，含 frontmatter）
  VERSION           （或在 frontmatter 内记版本，二选一，全仓统一）
  files/            （可选：脚本、模板、参考文件）
  examples/         （可选：调用示例与验收样例）
```

SKILL.md frontmatter 必备字段：`name`、`description`、`version`、`owner`（属主 agent）、`updated`（日期）、`platforms`（适用体系，如 hermes / claude / 通用）。正文必备小节：用途、何时用、步骤、验收或自查点。正文与字段的具体模板由 Muse 出 v1，报 BOSS 过目后定版。

### B3.2 中央仓与分发

- **中央仓在 GitHub**：新建技能专用私有仓（或经 BOSS 同意后用总线仓子目录，原则同 A3，专用仓优先）；此处 GitHub 是「仓」而非 A2A 任务通道，任务派发仍走总线，两者不混。
- **NAS 镜像**：Gitea 侧同步只读镜像，与全局分工一致；NAS 本地节点可就近从镜像拉取。
- **各 agent 按需拉取**：节点只拉自己要用的技能目录，拉取后在本机按各自体系的目录放好；**禁止各节点回写中央仓**，改进走投稿：改好后投回中央仓投稿区（或总线转投），由属主或 Muse 审核合并、升版本。
- **版本规则**：版本号三段式（主.次.修订）；不兼容改动升主版本并在 SKILL.md 记变更说明；各节点回执里注明自己在用的技能名 + 版本，便于出问题时定位。

### B3.3 与现有体系的格式映射

| 维度 | 中央仓标准 | Hermes skills | Muse custom-skills |
|---|---|---|---|
| 骨架文件 | SKILL.md | SKILL.md（原生即此格式） | SKILL.md（同名同骨架） |
| 元数据 | frontmatter 五字段 | 其技能索引字段与标准字段做对照表，缺 owner / version 的在拉取落地时补记 | 同左，落地目录为 custom-skills |
| 附带文件 | files/ 子目录 | 按其技能目录习惯平铺或子目录均可，落地脚本做一次路径转换 | 同左 |
| 不兼容部分 | —— | 依赖 Hermes 专有工具的技能标 `platforms: hermes`，不强行移植 | 依赖 Muse 专有工具的同理标注 |

原则：映射解决「能落地」，不追求「全通用」；带专有依赖的技能如实标注适用体系，避免别的节点拉去用不了还以为是技能坏了。
